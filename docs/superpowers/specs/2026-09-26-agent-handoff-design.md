# Agent 交接紀錄設計

## 目的與範圍

目前每個階段的 prompt 要求 agent 在回覆結尾附上 `<result>`，但其中的 `blocked`、`concerns` 只會印在終端機並保留於 log。下一位 agent 主要讀取 worktree 裡的程式碼與 `.flow/` 檔案，因此重要疑慮可能沒有進入下一階段。本設計讓需要後續處理的資訊持久化、可追蹤、可在開 PR 前核對，同時維持「是否通關由程式檢查檔案、diff、測試與經驗證的審查 JSON」的原則。

成功條件：每個成功的 agent 步驟都明確回報有無待處理事項；下一階段能讀到未結事項；重試、代打和 resume 不會重複、抹除或錯誤結案；有影響驗收或測試可信度的未結事項時不會開 PR。一般對話摘要不進入交接紀錄。

## 採用的方式

正式紀錄放在 `.agentflowctl/runs/<id>/handoff.json`，由程式原子寫入；agent 的 prompt 不把它當作可編輯的交接檔。每次 agent 呼叫前，程式從正式紀錄產生 `.flow/handoff-context.md`，只列出這一步需要處理的未結事項。每次呼叫後，agent 必須寫出 `.flow/handoff-response.json`，回報新增事項與處理結果；即使沒有事項，也要寫出空陣列。程式用 zod 驗證、合併至正式紀錄，並移除暫存回覆檔。所有 prompt 都要說明這兩個檔案的用途；審查者原本「只能寫審查 JSON」的限制須加入交接回覆檔例外。

交接檔與正式審查 JSON 分工：`plan-review.json`、`review.json`、`plan-arbiter.json` 的裁決仍決定原有審查轉移；交接紀錄只追蹤後續要處理的資訊，不取代裁決，也不因 agent 自稱 `blocked` 而自動停下。`feedback.md` 繼續存放本輪關卡失敗原因；持續追蹤的事項不放在這個會被清除的檔案中。

不採用只解析 `<result><concerns>`：它目前允許缺失或格式錯誤，文字也沒有事項 ID、處理階段與結案證據。不採用直接讓 agent 編輯共享的 `.flow/handoff.md`：它容易在重試或代打時被覆寫，無法可靠區分已接受與半成品。

## 資料模型

正式紀錄是帶版本的 JSON 文件：`{ version: 1, issues: [...] }`。每個事項包含穩定 `id`、`source`（階段、步驟、實際 agent、邏輯呼叫識別碼）、`kind`（`action` 或 `info`）、`summary`、`evidence`、`targetStage`、`status`（`open`、`proposed_resolved`、`resolved` 或 `accepted`）、`resolution` 與更新時間。`action` 表示後續必須處理或作出明確判斷；`info` 只供參考。作者可以提出 `proposed_resolved` 並附具體檔案、commit 或檢查結果，但只有後續審查者能將它改為 `resolved`，或以理由標成 `accepted`（確認無須修改）。沒有證據的「已解決」不能結案。程式驗證 ID、狀態轉移、必填欄位和所引用的既有事項；文字理由的技術正確性仍交給下一輪審查判斷。

`handoff-response.json` 為 `{ newIssues: [...], dispositions: [...] }`。新增事項不由 agent 指定正式 ID，程式依成功的邏輯呼叫識別碼和項目序號產生，避免碰撞。邏輯呼叫識別碼由 run、階段、任務與 phase、審查輪次、panel 位置和實際 agent 組成；同一步驟因中斷重跑時保持不變，進入下一輪時改變。處置引用既有 ID，包含處理方式、理由及證據。`info` 事項只需保存與呈現，不阻擋 PR；`action` 事項必須在目標階段或最終審查獲得處置。相同問題由多位審查者提出時，程式不憑自然語言猜測相同；可由後續處置明確引用同一事項，原始來源仍各自保留。

## 流程與關卡

1. 呼叫 agent 前，程式產生只包含相關未結事項的 `handoff-context.md`，清除上一個步驟留下的 `handoff-response.json`。
2. agent 完成既有產出後寫 `handoff-response.json`。程式先完成該步驟原有的檔案與測試檢查，再驗證交接回覆；缺失或格式錯誤依該步驟既有重試規則處理，不能當成空清單。
3. 只有整個步驟成功，才把交接回覆合併至正式紀錄。若原有檢查失敗、執行失敗或額度用完，這次回覆不生效，半成品依原有 reset 流程還原。
4. 計畫進入實作前，未處理的 `action` 事項必須由計畫審查或仲裁作出處置；程式不把 XML 的 `blocked` 當作裁決。若審查 JSON 核准，但交接回覆新建 `action` 或留下屬於該關卡的未結事項，視為不一致的審查輸出，重試該審查步驟。
5. 最終程式碼審查須看到全部與實作相關的未結 `action` 事項。每位 reviewer 的裁決仍須有效；所有 reviewer 核准、既有 verify 通過，且沒有未結 `action` 事項時，才可進入 `pr`。若審查 JSON 核准，但交接回覆新建 `action` 或留下未結事項，同樣重試該審查步驟。若 reviewer 認為事項已解決或不影響驗收，須提交附理由的處置。

## 邊界條件

| 情況 | 規則 |
| --- | --- |
| 無疑慮 | 回覆檔仍必須有 `newIssues: []`、`dispositions: []`。 |
| Agent 失敗、額度用盡或代打 | 不合併失敗呼叫的交接回覆；代打重新產生。 |
| Ctrl-C 或程序在合併附近中斷 | 使用由邏輯呼叫識別碼導出的穩定事項 ID，寫入正式紀錄採原子替換；resume 再合併同一回覆不產生重複項。若步驟尚未標記成功，依既有規則重跑該步驟。合併前先把經驗證的回覆存成同一識別碼的暫存收據，狀態儲存成功後才清掉；resume 可以重播收據，避免檔案已提交但交接遺失。 |
| 舊版進行中 run | 正式紀錄不存在時視為空的 v1 紀錄，不要求舊步驟補交；resume 後執行的新步驟採新格式。 |
| `feedback.md` 被成功關卡清除 | 正式交接紀錄不隨之刪除。 |
| 不存在的 ID、無理由結案、作者自行把事項標為已審查結案 | 回覆格式驗證失敗，回到相同 agent 步驟重試。 |
| 後續審查發現問題重現 | 可新增引用原事項的新事項，保留原結案歷史，不覆寫舊證據。 |
| 多位 reviewer | 各自的回覆分開驗證與合併；最終裁決依既有 quorum 規則，任何未結 `action` 都阻止進入 PR。 |
| 匿名仲裁 | `handoff-context.md` 對仲裁者只列問題內容與證據，不列來源 agent；完整來源只在 worktree 外的正式紀錄。 |
| 回覆 XML 缺失或寫 `blocked` | 不改變關卡；必填交接 JSON 與既有確定性檢查仍須通過。 |

## 驗證與文件

在 `schemas.ts` 定義交接輸入與正式紀錄 schema；在獨立模組實作原子讀寫、合併及階段投影，讓 `engine.ts` 只呼叫清楚的介面。測試涵蓋缺失與無效回覆、空清單、重試與代打、resume 冪等、無效結案、多 reviewer、匿名仲裁、舊 run、PR 前未結事項。更新所有 prompt 與 `README.md`，並執行 typecheck、測試與 build。

這項設計不能從 agent 的文字推斷真正的技術正確性；它保證資訊有明確去處、狀態可追蹤，且程式可檢查必要的交接與結案程序。既有測試、diff 和正式審查仍是內容判斷的關卡。
